<div class="about-text" style="max-width: 800px; margin: 0 auto 40px auto; text-align: left;">

OmniTool is a Python application for automating **3ds Max scene preparation and render-farm job
submission**. Its defining trait is reach: a single core library runs from three completely
different contexts (a command line, a PyQt desktop GUI, and natively inside 3ds Max through
`pymxs`) with the same code doing the work in each.

Just as interesting is how it ships. OmniTool is delivered as a self-updating, single-file
executable to roughly **130 machines across two independent studios**, and a large share of the
engineering went into making that distribution survive real-world studio constraints: endpoint
security (SentinelOne EDR), locked-down accounts, flaky drive mappings, and the quirks of
embedding a Qt app inside Max.

</div>

## How It Works

<Expandable title="Architecture">

The core library has *zero* UI knowledge: the CLI and GUI are thin shells over it. The connection
is injected by a `get_connection()` factory that auto-detects whether OmniTool is running natively
inside Max or talking to it externally (COM / socket). A Python 3.7 floor keeps it compatible with
the interpreter bundled in Max 2022, all the way up to 3.12 in Max 2026.

```text
omnitool/
├── connection/    Transport layer (COM, socket, native pymxs)
├── max/           MXS execution, scene operations
├── sini/          Sini IgNite / Forensic / Unite wrappers
├── pipeline/      Scene-prep orchestrator, submission logic
├── diagnostics/   Health checks, INI sidecar caching
├── models/        Pure data objects (reports, configs, manifests)
├── config.py      Farm paths, defaults
└── cli.py         CLI entry point
```

Common commands across every context:

```bash
# Diagnose connection + scene health
omnitool diagnose --scene shot_001.max

# Prep a scene (cleanup, relink, preflight)
omnitool prep --scene shot_001.max

# Force fresh diagnostics, bypassing the INI cache
omnitool diagnose --scene shot_001.max --force
```

</Expandable>

<Expandable title="Surviving Studio EDR">

Shipping a PyInstaller binary into a studio running SentinelOne meant the packaging choices *were*
the feature. Each setting in the build spec exists because an alternative tripped the
endpoint-security stack:

- **onefile, not onedir:** SentinelOne flagged the onedir launcher + `_internal\` DLL layout as DLL sideloading. The studio whitelist applies cleanly only to the single-file build.
- **UPX disabled:** UPX-packed binaries trip static analysis regardless of payload.
- **Redirected runtime tmpdir:** the bootloader extracts to `%LOCALAPPDATA%\OmniTool\runtime` instead of `%TEMP%`, reducing AV friction and avoiding orphaned extraction folders.
- **Explicit AppUserModelID:** set before `QApplication` starts so Windows shows OmniTool's icon instead of the generic embedded-Python feather.

</Expandable>

<Expandable title="Install & Update Flow">

The exe lives in a `dist\` folder on each studio's share and users only ever run `install.bat`,
which copies it to a folder on the desktop, drops a shortcut, installs the Max startup listener,
and writes a studio sentinel naming the share the machine follows. `uninstall.bat` reverses every
step in pure batch, with no dependency on the exe. The app refuses to start straight off the share:
a running share copy locks the file and blocks the next push, while a copy only takes a read handle.

There is no background updater. The app checks the share itself:

1. **When:** two seconds after startup on a background thread, when the window is activated (at most once a minute, no prompt), and whenever the user clicks Reload.
2. **How:** the file date of the share's exe against the installed one (the installer keeps the share's date when it copies). A local build newer than the share is never "updated" backwards, and an unreachable share is silent: the check gives up after four seconds.
3. **What the user sees:** the Reload button turns green and reads Update. At startup a prompt also offers the build, with "Not now" remembered per build and a "stop asking" tickbox.
4. **What Yes does:** the app writes a small waiter script, closes, the waiter runs the share's installer once the exe is released, and the app reopens on the new build.

The first version did this with a per-user scheduled task and a PowerShell script. It was retired
because the PowerShell hop flashed a console window on every launch; the installer and the app now
clean up what it left behind.

</Expandable>

<Expandable title="Build & Release">

One `build.bat` does the whole release:

1. Archives the outgoing exe, then commits and tags the source, so any build that shipped can be reproduced with a checkout.
2. Builds the single-file exe.
3. Asks for a channel, test or live. A test push writes a separate exe and its own installer next to the live build, never over it, and nobody is offered a test build automatically.
4. Pushes to both studio shares and byte-checks the exe on each, or installs on this machine only.

</Expandable>

## Engineering Highlights

<div class="about-text" style="max-width: 800px; margin: 0 auto 40px auto; text-align: left;">

- **Robust drive-path resolution:** The SQLite DB root resolves to the mapped `T:` drive when present and falls back to its UNC equivalent, because fresh logons and Deadline workers don't always have login-script drive mappings in place.
- **Crash-free in-Max listener:** The job-queue pump was moved off a `System.Windows.Forms.Timer` (which faulted re-entrantly inside the .NET↔MaxScript marshaling layer) onto a native MaxScript `rollout timer` hosted in an off-screen dialog, eliminating a class of unhandled-exception crashes.
- **In-Max listener by design, not everywhere:** The GUI talks to Max through a startup script that opens a local socket. After connecting, the app compares the listener's version and asks for a Max restart if it is stale; background Max instances (render nodes, batch mode) never start it.
- **Supportable by other people:** A rotating session log, a fatal-only crash log, crash dumps, a startup timing trace and per-scene fix logs, each tied to one kind of problem in the user docs, so a bug report arrives with the right file.
- **Two independent studios:** Each studio has its own bundle copy, its own database, and its own push cadence, with no cross-studio fallback: a machine pulls only from the studio it was installed from.
